# UI translations

The tray app and the forwarder show their UI in 20 languages. This page is for
developers: how a string gets translated, how the language is chosen, and what
stays English on purpose.

## What is translated and what is not

Translated: everything the two GUI processes draw themselves. That covers
menus, dialogs, tooltips, message boxes, tray balloons and the settings dialog.

English on purpose:

- **Logs, crash dumps and support bundles.** The maintainer reads them, and
  `problem_scan` matches curated patterns that only work in one language.
- **`polyctl` output.** Scripts parse it.
- **Text the core or the device produces** (the `msg` field of a progress
  event, a device error). The GUI translates its own wording and inserts that
  text as a value. The core stays Qt-free and language-free, so a German tray
  attached to a daemon gets German chrome around English detail.
- **Anything drawn on a keycap**, keycodes, layer names the keyboard reports,
  and file names.

## Choosing the language

`main_app` resolves it once, before either tray app builds a widget
(`gui/i18n_qt.prepare`):

1. `POLYHOST_LANG` in the environment, for one run. Takes a code or `pseudo`.
2. The `ui_language` setting, if it names a shipped language. `auto` is the default.
3. The OS UI language list (`QLocale.system().uiLanguages()`), first match.
4. English.

Matching rules (`i18n.match_os_language`): a regional variant uses its base
language (`de-AT` → `de`). Any Portuguese uses `pt_BR`. Chinese is decided by
script, then region: `Hant`, `TW`, `HK` and `MO` give `zh_TW`, and everything
else gives `zh_CN`.

⚠️ The OS UI language is not `locale.getlocale()`, which on Windows returns the
regional format setting. It is not the input layout either: this app switches
that itself whenever the keyboard changes language.

A change in Settings applies on restart, and the dialog offers to restart the
tray. In client mode only the GUI restarts. The daemon keeps the keyboard.

## Marking a string

```python
from polyhost.i18n import _, _f, _nf, N_

menu.addAction(_("Settings…"))
label.setText(_f("Firmware {version} is available", version=v))
status.setText(_nf("{n} bundle flashed", "{n} bundles flashed", n))
LABELS = {"fontpack": N_("font pack")}   # module constant; _(LABELS[k]) where shown
```

- One sentence is one msgid. Never translate fragments and concatenate them;
  word order differs between languages.
- Placeholders are named (`{version}`, never `{}` or `%s`). A translator sees
  only the msgid, so the name is their only clue.
- Use `_f` / `_nf` for any inserted value. Under Arabic and Persian they wrap
  each value in Unicode isolates (U+2068 … U+2069), so `1.15.2` or a path keeps
  its own direction inside right-to-left text.
- ⚠️ A function that calls `_()` must not also assign `_` (`ok, _ = f()`,
  `for _ in …`). Python then treats `_` as local to the whole function, and the
  call raises `UnboundLocalError`. The marking test catches this.
- An ambiguous short msgid gets a `# TRANSLATORS:` comment on the line above,
  for example to say whether "Flash" is a verb.
- A literal the scanner flags but that must stay as it is (a product name, a
  file filter) gets `# i18n: skip` on its line.
- Code that reads a widget's text back must read data instead
  (`combo.currentData()`, not `currentText()`). The settings dialog stores
  codes for this reason.

## Updating the catalogs

```bash
pip install -r tools/requirements.txt          # Babel, for extraction only
python scripts/i18n_strings.py unmarked        # literals still unmarked
python scripts/i18n_strings.py update          # write polyhost.pot, merge every .po
```

The app reads the `.po` files in `polyhost/res/locale/` directly at startup.
There is no compiled `.mo`: a generated binary beside its source is a second
copy that can drift. Fuzzy and empty entries fall back to English.

`tests/i18n_test.py` checks, for every catalog:

- every placeholder survives (a dropped `{version}` makes `_f` raise on screen)
- markup tags and `&` mnemonics survive
- plural entries have the language's number of forms
- the catalog covers the template, and the template matches the code
- no UI module shows an unmarked literal or shadows `_`

The scanner sees only literals passed straight to a Qt text call. A string
that reaches a widget through a variable is invisible to it. To find those,
run the app with `POLYHOST_LANG=pseudo`: every marked string appears accented,
padded by 40 % and in brackets. Unbracketed text was never marked, and a
bracket cut off by its widget marks a layout too narrow for German.

## Right-to-left

Arabic and Persian set `Qt.RightToLeft` before the first widget exists. Qt
mirrors every layout, menu and dialog from that. `ZoomableGraphicsView` pins
itself left-to-right, because it draws the physical keyboard, which does not
flip. Check a dialog in RTL without a translation by running with
`POLYHOST_LANG=ar` or Qt's `-reverse` flag.

## Qt's own strings

`install_qt_translator` loads `qtbase_<code>.qm` from the PyQt5 wheel, which
translates standard buttons and the file dialog. The wheel ships no catalog
for Vietnamese or Indonesian, so those two keep English standard buttons.

## Translation status

The 19 catalogs were drafted by machine and are awaiting review by native
speakers. Fix a translation by editing its `.po` file. A wrong translation on
a firmware-flash dialog is worse than English, so if in doubt, empty the
`msgstr`. The entry then falls back to English.
